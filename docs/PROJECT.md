# 开发盘点与下一步（2026-10-29）

## 产品目标（本轮已确认）

个人使用的 AI 伴侣 App：首先在 iPhone 本地运行，聊天记录、记忆和主要业务逻辑保存在手机，联网调用模型 API；希望后续也能适配 Android。互动应支持多个角色、群聊、主动发言以及一次连续发几条消息。

本轮范围：精简架构、改善记忆基础，为这些功能明确演进路径。不是本轮把现有网页变成原生 App。

## 问题的根因与优先级

### P0：先让记忆写入可靠

1. 两套抽取逻辑存在行为差异：本轮统一；原来非法 JSON 可被当成成功空结果，本轮修复。
2. 同一会话重复抽取会堆积完全相同的事实：本轮加入原子查重写入。
3. marker 同时承担会话边界和抽取进度，失败恢复脆弱；后台 daemon 线程退出后没有持久任务恢复。
4. 抽取只留 `source_quote`，缺少原始 message ID、会话范围、事实有效时间及版本。相同文本不一定表示同一次事件。
5. 同一角色多连接同时聊天，MAX(turn_index)+1 不是原子分配；模型输出结束前输入未持久化，失败可能丢轮次。

下一步应先引入小而明确的抽取任务表：范围 `[start_message_id, end_message_id]`、状态、重试次数、错误；按固定范围执行并在重启后恢复。不要继续让删除 marker 兼任所有失败恢复。

### P1：让记忆可关联、可更新、可衡量

**关联不是把相似文本随便连线。** 先定义记忆代表什么：事实、事件、偏好、承诺；再定义 `related_to`（相关）、`supersedes`（更新）、`contradicts`（冲突）、`follows`（时序）。边要有来源或解释；共处一个 session 不自动等于因果关系。

建议写入流程：

1. 从用户原话提取事实，并保存消息来源和事实时间。
2. 用关键词和语义候选查找已有记忆。
3. 决定新增、补充证据、更新旧事实或保留冲突；不要仅凭相似度阈值删除。
4. 写入关系边和版本，更新画像摘要。原始消息是依据，摘要可重建。
5. 查询先找直接相关记忆，再做有数量和相关度限制的一跳扩展，避免整张图灌入 prompt。

目前没有语义模型配置，不能声称“已解决语义重复”。在 120 条规模下，先用可解释检索和评测验证，不需要先引入图数据库或独立向量服务。

**召回弱的具体原因：** 只用本轮输入、中文字符片段噪声、候选数量截断、旧评分偏重要性与新鲜度、没有关系扩展和语义理解。“那后来呢”需要近期话题辅助查询，不能只查这四个字。本轮只修复其中的排序、精确重复占位、top_k 和 FTS 标识问题。

先建人工标注集，再决定向量/重排投入：至少覆盖姓名城市、偏好、事件进展、约定、否定纠正、代词追问、跨话题和无相关记忆。记录 Recall@5、重复占位率、无关召回率、延迟与调用成本；每个问题给出期望 note ID，记录改动前后结果。没有这组评测前，不给出“召回提升百分比”。

### P2：消息模型支持自然聊天和群聊

当前 `UNIQUE(user_id, persona_id, turn_index, role)` 明确限制每轮一条 assistant；角色 ID 还兼任私聊会话标识，用户的角色列表用 CSV 保存。

迁移方向（先设计迁移和回退，再改真实库）：

- `conversation`：私聊或群聊的独立 ID。
- `participant`：会话参与者，区分用户与多个角色。
- `message`：独立消息 ID、发送者、会话内顺序、回复对象、生成批次、发送状态。
- `generation`：一次触发及其 0..N 条回复；`trigger` 区分用户输入、定时、事件。
- 记忆单独声明范围：用户私有、角色私聊、某个群聊；群成员不能自动获得所有私聊记忆。

先做单聊多条消息：模型生成结构化消息数组，逐条展示、逐条保存，支持用户插话与取消。群聊再增加“谁回应、是否回应、是否继续”的调度；限制每次生成的消息数和连续模型发言，避免角色互相无限触发。

### P3：独立手机端

当前 Python 服务适合作为行为原型和回归基准。最终 App 的本地 SQLite、抽取调度、召回和模型调用需要在移动端实现；复用数据契约、提示词和测试场景，不把 Python HTTP 服务原封不动当作手机本地架构。

| 路线 | 适用与代价 |
|---|---|
| Flutter（优先评估） | 一套客户端覆盖 iOS/Android，业务与界面复用较多；需要迁移为 Dart，通知和后台处理仍需平台适配 |
| Swift 原生 iOS + Android 原生 | 适合优先深入 iOS 平台能力；未来两端界面与平台逻辑维护成本较高，可共享协议和测试 |
| 延续网页再封装 | 能复用当前网页，但必须实现本地数据库、业务逻辑、模型请求和平台集成；仅套壳仍依赖现有服务器 |

这是基于目标的建议，不是本轮已确认的框架选型。Flutter 官方确认可用单一代码库覆盖多平台：[平台集成文档](https://docs.flutter.dev/platform-integration)。先用一个最小手机原型验证：本地消息保存 → API 流式回复 → 本地精确去重 → 关闭重开仍可查看，再迁移更多界面。

### P4：主动触达

分三种能力实施：

1. App 前台：根据时间、上文或事件决定是否主动开口；支持静默时段、频率限制与关闭开关。
2. 本地通知：预先生成或固定内容的提醒，点击后再调用模型继续聊天。
3. App 长期不在前台时动态生成新消息：需要接受操作系统后台调度的不确定性；如果要求服务端主动生成再远程推送，则增加一个可选服务，这是另一项部署取舍。

iOS 的后台任务执行时机由系统决定，不能承诺每分钟醒来运行一次模型：[Apple 后台策略](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)。Android WorkManager 的周期任务最小间隔是 15 分钟，也不等于精确定时：[Android 工作请求](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)。跨平台框架不消除这些平台限制。

## 防御代码怎么判断

保留：数据隔离、来源校验、事务、明确失败状态、正文与思考分离、真实 bug 的回归测试。

简化：重复业务实现、同一数据的重复模型、重复配置列表、长篇开发历史嵌入代码、没有用途的空壳分层。

待重新讨论的产品规则：关系进度“只能上涨”、摘要列表固定截断、常驻记忆类型。这些是产品策略，不是安全要求；不应该以防御代码的名义固化。允许关系疏远、偏好改变时，要有明确更新语义和测试。
