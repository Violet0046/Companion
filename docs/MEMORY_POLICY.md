# 记忆保存与使用规则

2026-10-29 第一轮用户审阅。本文区分已确认的产品规则与待验证的实施建议。
原话和逐案例审阅意见保存在 gitignored 的 `memory/reviews/`；公开文档仅保留通用规则。

## 已确认的六项规则

| 内容 | 是否保存 | 使用边界 |
|---|---|---|
| 条件承诺 | 随相关经历保留，带触发条件 | 同一事件出现结果、条件满足时可自然想起；不是无条件欠账 |
| 有进展的现实事件 | 保存事件时间、截至时间、来源 | 相关话题或明确进展时召回；普通问候不应强行追问 |
| 随口吐槽的日常小事 | 默认不作为长期笔记保存 | 留在原始聊天；不能因为有时间地点就认定有长期价值 |
| 当天疲惫等短期状态 | 不建笔记，但允许作为短期上下文 | 应有时间和过期机制；不能变成永久画像 |
| 用户明确建立的共同想象经历 | 可以保存为有意义的共同经历 | 标记共同想象，保留人设背景与互动连续性，不冒充现实事件 |
| 当次选择和话题边界 | 不升级为长期偏好 | 仅在当前互动适用；是否并入经历取决于整个片段的价值 |

这些规则不意味着每类内容一律保留或丢弃。例如日常小事若被用户明确要求记住，或产生持续后果，仍可成为经历。
当次选择是否值得单独建经历尚未获得一概而论的确认；建议并入有意义的片段，不为单句选择建笔记。

## 保存资格与召回资格分开

保存回答“将来可能值得想起吗”；召回回答“现在想起它会帮助这次交流吗”。
允许长期保存的内容，也可以在绝大多数轮次都不召回。

建议给候选召回增加以下验收标准（尚未接入当前检索器）：

1. 普通问候和无关闲聊：不因重要性高或事项未结束就拉回旧事件。
2. 用户主动提及某事：结合近期上下文定位同一事件，使用最新有证据的状态。
3. 新进展涉及旧约定：找出相关条件承诺，确认条件的含义与是否满足，再决定是否提起。
4. 约定已履行或被撤回：不继续提醒；没有证据时不得把未知写成未履行。
5. 曾经提起不代表以后每轮都提起；提出后应结合后续回应抑制重复。此规则不等同于后台主动通知。

条件承诺第一版可包含在经历文本中，写清“谁、什么条件、承诺什么、履行情况未知”，不必立即增加任务系统。
如果后来确实需要独立状态跟踪，再设计兑现、撤回及使用记录。

## 短期状态：已确认方向，尚未实现

架构仍是两层长期记忆（经历、事实），加一份有期限的当前状态。当前状态不进入 note_link，也不参与长期事实统计。

建议最小数据：用户/角色范围、状态项、用户自述内容、来源消息、表达时间、到期时间。
一个状态项仅保留当前有效值；历史由原始聊天保存，不为状态建立第二套历史笔记库。
例如“精力：用户表示有点累”，不要自动升级成数值情绪评分，也不要猜测原因。

建议生命周期：

- 用户明确表达时建立或更新；重复的表达可以刷新，但不能因助手提到它而续期。
- 用户明确说状态解除时立即撤销；普通问候不等于状态解除。
- 模型构造上下文时只读取尚未过期的状态，过期后回到未知，而不是推断已经恢复。
- “今天”不得延续到用户当地的次日；更具体的持续时段应按原话处理。
- 没有明确持续时长时，可先试用 6 小时上限。这是待验证的产品默认值，不是用户已确认的规则，更不是状态真实持续时间。
- 状态可以影响回复长度、语气和建议，但不要求每次重复“你是不是累了”。

建议仍存本地 SQLite 的小状态表，以便重启后保持一致；读取时按时间过滤，无需定时清理进程。
表结构、范围以及时限还未迁移，也没有接入正式 prompt。先用时间推进的虚构样例验证：过期、跨日、显式解除、重复表达、不相关话题。
若原话已在近期聊天中，状态区不再逐字重复整段，只表达当前有效状态及来源时间。
